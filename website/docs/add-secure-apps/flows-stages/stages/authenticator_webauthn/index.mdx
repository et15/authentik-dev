The WebAuthn / FIDO2 / Passkeys Authenticator setup stage enrolls a WebAuthn authenticator for the current user.

## About the WebAuthn authenticator setup stage

This stage supports common WebAuthn authenticator types, including:

- security keys such as YubiKey or Google Titan
- platform authenticators such as Windows Hello, Touch ID, or Face ID
- passkeys stored by operating systems or password managers

Enrolled authenticators can later be used with the [Authenticator Validation stage](../authenticator_validate/index.mdx).

## Configuration options

- **User verification**: require, prefer, or discourage built-in user verification during registration.
- **Resident key requirement**: control whether the authenticator should create a discoverable credential.
- **Authenticator Attachment**: restrict enrollment to platform authenticators, cross-platform authenticators, or leave it unrestricted.
- **Hints**: browser hints that influence which authenticator is preferred during enrollment.
- **Device type restrictions**: limit enrollment to specific WebAuthn device types.
- **Attestation requirement**: require cryptographic proof of an authenticator's claimed device identity.
- **Backup eligibility**: restrict enrollment based on whether the credential can be backed up or synced across devices.
- **Key protection**: restrict enrollment to authenticator models that protect their keys in specific ways (for example in a secure element).
- **Maximum registration attempts**: maximum number of failed registration attempts before the stage denies access. A value of `0` disables the limit.
- **Authenticator type name**: optional friendly name shown to the user in self-service settings.
- **Configuration flow**: optional authenticated flow that lets users enroll this authenticator from user settings.

## Flow integration

Use this stage in an enrollment or user-settings flow where the user should register a passkey or hardware key.

To require those devices during login, add an [Authenticator Validation stage](../authenticator_validate/index.mdx) to the authentication flow and allow the **WebAuthn** device class.

If you want passkey autofill on the login form itself, configure the [Identification stage](../identification/index.mdx#passkey-autofill-webauthn-conditional-ui) to reference a WebAuthn-capable Authenticator Validation stage.

## Notes

### User verification

**User verification** controls whether authentik requires, prefers, or discourages user verification on the authenticator itself. On platform authenticators such as Windows Hello, that can determine whether a PIN or biometric check is required.

### Resident key requirement

For passkey-based passwordless login, set **Resident key requirement** to **Preferred** or **Required** so the created credential is discoverable.

### Authenticator attachment

Use **Authenticator Attachment** when the flow should prefer either removable authenticators such as YubiKeys or built-in authenticators such as Touch ID, Windows Hello, or password-manager passkeys.

This controls the `authenticatorAttachment` parameter sent to the browser during WebAuthn registration:

- **No preference is sent**: the browser can offer any available authenticator.
- **Platform**: prefer a non-removable authenticator built into the device, such as Touch ID, Face ID, or Windows Hello.
- **Cross-platform**: prefer a roaming authenticator, such as a YubiKey or Google Titan.

If [WebAuthn hints](#webauthn-hints) are configured and this option is left unset, authentik infers an attachment value from the selected hints for backward compatibility with older browsers.

### WebAuthn hints

:::info
Hints are advisory and browsers can ignore them based on available authenticators or platform capabilities.
:::

Optional hints can guide the browser toward a preferred authenticator type during registration:

- **Security key**: prefer registering a credential with a portable FIDO2 device such as a YubiKey.
- **Client device**: prefer registering a credential with a built-in platform authenticator such as Touch ID or Windows Hello.
- **Hybrid**: prefer registering a credential using a platform authenticator on a nearby mobile device, typically through a QR code.

The order of selected hints matters. For example, selecting **Security key** before **Hybrid** asks the browser to prefer security keys before hybrid registration.

For backward compatibility with older browsers that do not support hints, authentik automatically infers the `authenticatorAttachment` parameter from the selected hints when **Authenticator Attachment** is not explicitly set:

- Only **Security key** and/or **Hybrid** hints: `cross-platform`
- Only **Client device** hints: `platform`
- If both client-device and cross-platform hints are selected, no value is inferred

### Duplicate devices

The **Prevent duplicate devices** option was removed in 2026.8. It compared attestation certificates, which manufacturers share across entire production batches, so it rejected legitimate enrollments of a second security key. No configuration replaces it, and no action is needed when upgrading.

### Device type restrictions

**Device type restrictions** are an allowlist for WebAuthn registration. When no device types are selected, authentik allows any WebAuthn authenticator that the browser and authenticator can register. When one or more device types are selected, authentik only allows registration when the authenticator returns an AAGUID that matches one of the selected entries.

The available device-type entries are populated from the [FIDO Alliance Metadata Service](https://fidoalliance.org/metadata/) data and additional AAGUID metadata bundled with the authentik release. This lets you restrict enrollment to specific hardware families or passkey providers listed in that metadata.

If you select specific device types, newly added metadata entries are not allowed automatically. Review this allowlist after authentik upgrades if your compliance policy should include newly recognized authenticators.

authentik also includes the special device-type `authentik: Unknown devices`. Select it only when you want to allow authenticators that return an AAGUID that is not present in authentik's device-type metadata. Authenticators that do not return an AAGUID cannot satisfy a device-type restriction.

### Backup eligibility

**Backup eligibility** restricts registration based on the WebAuthn **Backup Eligibility (BE)** flag, which an authenticator sets permanently when a credential is created. This flag distinguishes:

- A **single-device credential** (BE = 0): bound to one specific piece of hardware, such as a security key, or a platform authenticator (like Windows Hello or Touch ID) that has not been enrolled with a cloud-syncing passkey provider.
- A **multi-device credential** (BE = 1): eligible to be backed up or synced across devices, such as a passkey stored in iCloud Keychain, Google Password Manager, or a third-party password manager.

Options:

- **Any** (default): no restriction is applied. This matches the behavior prior to this option's introduction.
- **Required**: only credentials that are eligible for backup/sync are allowed to register. Use this to require passkeys that survive device loss.
- **Denied**: only credentials that are *not* eligible for backup/sync are allowed to register. Use this to require hardware-bound authenticators (security keys, or a device's local biometric/PIN authenticator) and reject synced passkeys and password-manager-backed credentials.

:::info
Unlike **Authenticator attachment**, which only distinguishes *platform* (built into the device) from *cross-platform* (removable) authenticators, **Backup eligibility** distinguishes whether a credential's private key can leave the device it was created on. A platform authenticator can be either: Windows Hello and Touch ID are typically single-device credentials, while an OS-level passkey enrolled with iCloud Keychain or Google Password Manager is a multi-device credential, even though both present as "platform" authenticators to the browser. Combine **Authenticator attachment: Platform** with **Backup eligibility: Denied** to allow only device-bound platform authenticators (Windows Hello, Touch ID, Android StrongBox) while still rejecting cross-platform security keys and any synced passkey.
:::

:::info
Backup eligibility is only checked at registration time, and only stored on newly-registered credentials (requires a version of authentik with this option available; check the release notes for the exact version). It is not re-checked on subsequent logins, so a credential that later becomes eligible for backup (for example, if an authenticator vendor changes its sync behavior) is not automatically re-evaluated. Existing credentials enrolled before this option was added are not retroactively restricted.
:::

:::caution
BE is a value reported by the authenticator. It is covered by the attestation/assertion signature, but nothing proves it is truthful. It also does **not** tell you whether the key lives in a security chip; see **Key protection**.
:::

### Attestation requirement

By default, authentik trusts the AAGUID (device model identifier) an authenticator reports without cryptographic proof; nothing in the protocol stops a client from claiming an arbitrary AAGUID. **Attestation requirement: Required** closes this gap:

- The authenticator must return a full attestation statement (not `none`) with a certificate chain for its attestation key.
- Its claimed AAGUID must exist in authentik's FIDO Metadata Service data (kept current by the `webauthn_mds_import` task) with at least one published trusted root certificate.
- The certificate chain must validate against one of those roots.

Registration is rejected if any of these fail.

:::info
This proves the manufacturer identity of the authenticator; it does not restrict *which* authenticators are allowed. Combine it with **Device type restrictions** or **Key protection** to define policy.
:::

:::caution
Requiring attestation rejects authenticators whose manufacturer does not participate in the FIDO Metadata Service, or that authentik's bundled metadata snapshot does not yet contain. Test with your users' actual hardware before enforcing it broadly.
:::

### Key protection

**Key protection** restricts registration to authenticator models whose FIDO Metadata Service entry declares specific `keyProtection` types. This is what lets you require, for example, that keys live in a security chip rather than in software.

Accepted types:

- `software`: keys are handled by software on the host
- `hardware`: keys are protected by hardware, isolated from the host OS
- `tee`: keys are held in a Trusted Execution Environment
- `secure_element`: keys are held in a dedicated secure element
- `remote_handle`: key material is stored outside the authenticator, wrapped by a key that never leaves it

A model can declare several types at once (a YubiKey 5 declares `hardware`, `secure_element` and `remote_handle`). The selection is the list of **accepted** types. With nothing selected, no restriction applies. **Key protection matching** defines how the types a model declares are compared with that list:

- **Any**: at least one declared type must be accepted. This is the weaker mode: a model that declares an accepted type next to an unaccepted one still passes.
- **All**: every declared type must be accepted, and at least one must be declared. A model that declares anything outside the list is rejected.

To allow only hardware-backed keys, select `hardware`, `secure_element` and `tee` (add `remote_handle` if you want to accept models such as YubiKeys that declare it) and use **All**. `software` is then never accepted, even when a model combines it with other types.

:::info
Key protection requires **Attestation requirement: Required**, and the API refuses configurations that combine them otherwise. The value comes from the metadata entry of the authenticator's AAGUID; without verified attestation that AAGUID is only self-reported and the check would prove nothing. Authenticators without a metadata entry, or without a trusted attestation root, are rejected.
:::

:::caution
`keyProtection` is the manufacturer's published claim about a *model*, taken from the FIDO Metadata Service. authentik does not verify it independently, and it only applies to newly registered credentials. It is not re-evaluated on later logins.
:::
